## 2. Technical feasibility

| Option | Verdict |
|---|---|
| Node 22 + `node:sqlite` (built in) + Express, vanilla JS PWA | **Chosen.** Verified here: `node:sqlite` works, npm registry reachable, no native build. One SQLite file, trivially backed up. |
| Supabase as backend | Not reachable from this sandbox (`api.supabase.com` returns 403). Could be the production store later; the repository layer isolates storage. |
| React/Vite SPA | Unnecessary build complexity for a two-person app. Rejected. |
| Native iOS app | Not required; mobile-first web app is installable on iPhone via "Add to Home Screen". |
| Auth | PIN per person (scrypt-hashed) + server session cookie. Simple, enough for a two-person household. Not a substitute for a managed identity provider if the app is exposed publicly. |

## 3. Data model (SQLite)

- `people` (id, name, pin_hash) — fixed: `asha`, `prabha`.
- `sessions` (token_hash, person_id, expires_at).
- `profiles` (person_id, json fields for dietary notes, allergies, dislikes, likes, restrictions, goals, cooking feedback, appliances, weekday cooking-time limit, meal frequency, budget, nutrition context, onboarding answers).
- `household` (single row: onboarding answers shared by both, appliances, batch-prep preference, budget, routine).
- `recipes` (id, name, cuisine, meal_types, active/prep/total minutes, servings, ingredients[], steps[], air_fryer settings, storage notes, nutrition estimate + source + uncertainty, tags, enabled).
- `recipe_outcomes` (recipe_id, date, person_id, rating, notes, modifications).
- `plan_entries` (date, slot [breakfast|lunch|dinner|snack], recipe_id, status, reason).
- `pantry_items` (name, quantity, unit, status [confirmed|estimated], updated_at).
- `pantry_moves` (proposed/confirmed deductions tied to a cooked meal, reversible).
- `shopping_lists` / `shopping_items` (name, qty, unit, checked, source).
- `memories` (id, scope [household|person], person_id, kind [one_time|lasting], text, active, created_at, expires_on).
- `notifications` (id, kind, title, body, due_at, read_at).
- `feature_requests` (id, text, status, draft_spec).
- `schema_migrations` (version) — ordered, forward-only migrations with documented rollback.

## 4. User flows

1. **First run:** set PINs for Asha and Prabha → sign in → onboarding checklist.
2. **Onboarding:** fill household routine, cooking time, appliances, meal frequency, budget, and per-person profile items. "None" / "Not sure" are explicit answers. Plan generation stays locked until required items are answered.
3. **Recipes:** add or edit recipes manually (no bundled recipe catalogue — none was supplied).
4. **Monthly plan:** generate for a month from the enabled recipes, avoiding memories' avoid rules and recent repeats; edit, swap, or repeat any slot.
5. **Cook:** open a recipe in step mode → mark cooked → review proposed pantry deductions → confirm or correct → record outcome/feedback → memory optionally saved.
6. **Shopping:** the app compares the next 7 days of plan with the pantry → missing items → add to a shopping list → tick purchased.
7. **Reminders:** 08:00 briefing (today's menu + missing items) and 20:00 prep reminder (tomorrow's meal + shopping) appear as in-app notifications.

## 5. Open questions (not assumed)

Kept as editable fields and onboarding items, not decided by the build:
- Other cooking appliances; weekday cooking-time limit; batch-prep preference.
- Allergies, further dislikes, meal frequency, portion preferences, food budget.
- Asha: postpartum stage, breastfeeding pattern, height, clinician guidance. Prabha: fitness goal and protein target.
- Hosting/backend choice and access; GitHub repository; Alexa setup; WhatsApp test configuration.
- Exact Govee and Europa model numbers.

## 6. Risks

- No recipes or nutrition data were supplied → the plan can only use recipes entered by the household; empty library is the honest starting state.
- Health content (Asha's hair fall, breastfeeding, supplements) is recorded as context only. The app does not diagnose or prescribe; it prompts for clinician review.
- Notifications are in-app only until web push is added; they only appear while the server is running.
- Single-process scheduler: fine for one household; must not be duplicated across instances.

## 7. Phased plan

- **Phase 1 (built now):** auth, profiles, onboarding, recipe library, monthly plan, pantry, deductions, shopping lists, memories, notifications/briefings, feature-request log, tests.
- **Phase 2:** conversational input (needs LLM provider decision), receipt/photo capture (vision provider), web push.
- **Phase 3:** WhatsApp Cloud API sharing (needs Meta app, verified recipients, approved templates, webhook URL).
- **Phase 4:** Alexa custom skill (verify reminders/announcement limits first), Home Assistant, Govee, Europa lock (only exact models with user-specific unlock events), ESP32-S3 desk bot.
